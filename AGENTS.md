# GTAR1 agent guidance

- GTAR1 is an independently runnable local-first Web/PWA in `web/`. Read applicable nested `AGENTS.md` files before editing. Keep changes within the requested scope and preserve user data and existing behavior.
- Original GTAR is the canonical development and release source: GTAR `dev` integrates development; GTAR `main` holds approved production releases. GTAR1 currently depends on approved GTAR releases. GTAR1 `main` is the public release source; `demo` is the public interactive demonstration. GTAR1 has no `dev` or staging branch. Use current `origin/main` for GTAR1 proposal or maintainer-authorized documentation/governance branches.
- Community contributors may fork GTAR1 and submit **DRAFT PRs targeting GTAR1 `main`**. These are proposals only and must not be directly merged into GTAR1 `main`, even with green CI. The owner evaluates proposals; accepted changes are independently reviewed and ported into original GTAR `dev`, with normal development, verification, QA, and release approval.
- Distinguish community proposals, owner-authorized GTAR1 documentation/governance work, and maintainer-authorized release synchronization in each PR. Include the issue, base/head SHAs, scope, validation evidence, and limitations. Owner authorization for documentation/governance work does not authorize direct integration of community product changes.
- Approved releases are promoted through original GTAR's existing release workflow. Maintainer-authorized synchronization supplies GTAR1 `main` with the approved public-release source snapshot and GTAR1 `demo` with the corresponding demo-compatible update. Preserve GTAR1-specific branding, configuration, demo data, independent governance, and public identity; GTAR1 is not a byte-for-byte copy. Synchronization is deliberate and controlled, never blind copying or automatic feature/source synchronization. Do not modify or import existing release infrastructure as routine contribution work.
- The owner alone controls preview QA, Ready for Review, permitted maintainer merges, and release/deployment authorization. No automatic tagging, merging, deployment, or release synchronization. Do not merge, tag, deploy, or mutate production without explicit owner authorization.
- From `web/`, run `npm ci`, `npm run lint`, `npm test`, and `npm run build` before handoff. Report failures accurately; do not weaken checks. The focused regression suite and execution instructions live in [web/tests/README.md](web/tests/README.md).
- Preserve GTAR1 branding, release identity, existing demo behavior/configuration, and Cloudflare configuration unless explicitly authorized. Do not import legacy release controllers or promotion machinery.
- Never commit credentials, secret values, private user content, or generated build output. Keep optional services separate so the core remains usable without sign-in.
- Preserve All Rights Reserved wording and third-party notices. Public visibility grants no reuse license. See [CONTRIBUTING.md](CONTRIBUTING.md) and [SECURITY.md](SECURITY.md).
